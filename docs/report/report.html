1. Introduction and Choice of Cloud Provider

The application is a full-stack Personal Expense Tracker (MERN stack): users register and log in (JWT), record categorized expenses, set monthly and per-category budgets with alerts, view charts and monthly reports, and export reports as PDF/CSV. It is naturally a three-tier application: a React single-page application (presentation tier), an Express/Node.js REST API (application/business-logic tier) and MongoDB (data tier). This report describes how it was containerized, deployed on AWS across public and private network tiers, and automated with a CI/CD pipeline, and justifies the design against the required non-functional requirements (NFRs).

Why AWS. AWS was selected because (i) it offers every building block the brief asks for as first-class managed services — VPC, NAT Gateway, Application Load Balancers with target groups, EC2 Auto Scaling Groups, Elastic Container Registry, Secrets Manager, Systems Manager, S3, EBS and CloudWatch; (ii) its Free plan ($100 credits, free-tier-eligible t3.micro/t3.small instances) allowed a realistic multi-AZ deployment at no personal cost; (iii) Terraform's AWS provider and GitHub Actions' official AWS actions are mature, enabling a fully reproducible infrastructure-as-code and CI/CD workflow; and (iv) it is the most widely used provider in industry, so the skills transfer directly.

Account constraints discovered and handled. The AWS Free-plan account is governed by an organization Service Control Policy that (a) allows only the ap-southeast-2 (Sydney) region, (b) denies Amazon DocumentDB / RDS cluster and instance creation, and (c) denies creating an IAM OIDC identity provider. The design was therefore deployed in Sydney, uses the brief's permitted alternative of a properly secured self-managed database instance, and authenticates CI/CD with a narrowly scoped IAM user instead of OIDC. Each constraint is documented as a limitation in Section 7.

2. Overall Architecture and Design Decisions

Request path. Browser → public Application Load Balancer (internet-facing, public subnets) → web tier (Nginx container serving the React build) → for /api/* Nginx reverse-proxies to the internal ALB (private subnets, not internet-reachable) → application tier (Express container) → MongoDB on a dedicated host in the private DB subnet.

2.2 Key design decisions

  • EC2 Auto Scaling Groups running Docker (instead of ECS/EKS): matches the brief's "Auto Scaling Groups" and "pull the new image onto the target compute instance", and keeps each tier's compute, scaling and security group independent.
  • Two load balancers: the public ALB fronts the web tier; a separate internal ALB fronts the API so that the application tier is reachable only from the web tier, as the brief requires.
  • Same-origin API: the browser calls /api on the same host; the web tier proxies it. The API is never exposed to the internet and no CORS surface is needed.
  • Release pointer in SSM Parameter Store: the pipeline publishes the image tag (git SHA); instances read it at boot, so instances launched later by auto scaling always run the current release.
  • No SSH anywhere: deployment and administration use AWS Systems Manager Run Command / Session Manager; no key pairs or port 22 rules exist.
  • Everything as code: about 100 AWS resources are defined in Terraform and can be recreated or destroyed with one command.

4. Containerization and CI/CD Pipeline Design

4.1 Containerization

  • Web image (frontend/Dockerfile): multi-stage — stage 1 builds the React app with Vite on node:20-alpine; stage 2 copies only the static files into nginx-unprivileged:1.27-alpine (non-root, port 8080). The Nginx config is a template whose API upstream and DNS resolver are injected per environment, and adds SPA routing, gzip, long-term asset caching, security headers and a /healthz endpoint.
  • App image (backend/Dockerfile): multi-stage — production-only dependencies installed with npm ci --omit=dev, runs as the non-root node user, with a Docker HEALTHCHECK. The backend was refactored into app.js/server.js for testability and graceful SIGTERM shutdown.
  • docker-compose.yml runs web, app and MongoDB locally on two separate Docker networks (web cannot reach the DB network), mirroring the AWS segmentation; the same compose file is used by the pipeline's integration test.
  • .dockerignore files keep node_modules, tests and any .env secrets out of the images.

4.2 CI/CD pipeline (GitHub Actions)

#JobWhat it does
1Backend unit testsnpm ci && npm test (Node test runner + Supertest: health, 404, auth guard)
2Frontend buildCompiles the React app to catch build errors
3Terraform fmt & validateRejects malformed infrastructure code
4Integration testdocker compose up --build --wait, then through Nginx: register a user → create an expense → list it; proves all three containers work together
5-6Build & push (web, app)Docker Buildx with layer cache; push to ECR tagged with the commit SHA
7Rolling deployPublishes the SHA to SSM, then runs the deploy script on each in-service instance one at a time via SSM Run Command (app tier first, then web) and waits for each container to pass its health check; finally smoke-tests the public URL until /api/health returns the new SHA and db: connected

Jobs 1-4 run on every push and pull request; jobs 5-7 run only on main. Concurrency control prevents overlapping deployments, and documentation-only commits skip the pipeline. Because each release is an immutable SHA-tagged image, rolling back means re-running the pipeline for an earlier commit.

5. Security Considerations

ControlImplementation and justification
Security groups per tier (least privilege)Five security groups chained by security-group references, not IP ranges: public ALB ← internet :80; web ← public-ALB SG :80; internal ALB ← web SG :80; app ← internal-ALB SG :5000; MongoDB ← app SG :27017. Each tier accepts traffic only from the tier directly in front of it.
Network segmentationSeparate public, private-app and private-DB subnets. App and DB hosts have no public IP and reach the internet only outbound through NAT. The internal ALB has no public address (resolves to 10.0.x.x only).
Secrets managementDB password and JWT secret are generated by Terraform and stored only in Secrets Manager; containers receive them at start into chmod 600 env files. Nothing is hard-coded in code or images; .env, *.tfvars and Terraform state are git-ignored.
CI/CD secretsThe pipeline authenticates with a dedicated IAM user whose key is stored as GitHub encrypted secrets (created and piped directly into GitHub, never displayed). Its policy only allows pushing to the two ECR repositories, updating the two release parameters and sending commands to instances tagged Project=expense-tracker.
IAM least privilegePer-tier instance roles: each can pull only its own image, read only its own release tag and write only its own log group; only the app role may read the app secret; the DB role may only write to backups/ in its bucket.
EncryptionAll EBS volumes (including DB data) encrypted at rest; S3 backups encrypted with public access blocked and a TLS-only bucket policy; ECR encrypted (AES-256).
Host and container hardeningNo SSH or key pairs; IMDSv2 required with hop limit 1, so containers cannot obtain instance-role credentials; web and app containers run as non-root; MongoDB authentication enforced.
Supply chainImmutable image tags, ECR scan-on-push, and tests + integration test gating every deployment.

Verified from the internet (evidence file 10-security-and-backup-tests.txt): the public ALB returns HTTP 200; a direct request to a web instance's public IP times out (blocked by its SG); the internal ALB resolves only to private addresses; the app and DB instances have no public IP.

Issue found and fixed by the pipeline. The very first run failed only at the web-tier deploy step: the Auto Scaling Group had just replaced an instance that was not yet registered with Systems Manager. The deploy script was changed to skip still-booting instances (they self-deploy from the published tag at boot) and the CI user was granted ssm:DescribeInstanceInformation; every subsequent run has been fully green. 7. Non-Functional Requirements Justification

NFRDesign / implementation decisions that support itKnown limitations and improvements
ScalabilityStateless containers (JWT, no server sessions) behind load balancers; web and app tiers scale horizontally and independently in their own ASGs (2→4 instances); the DB tier is isolated so it can be scaled separately.Max 4 per tier to protect free credits (one variable to raise). Database scales vertically only → a MongoDB replica set / sharding or a managed cluster would scale reads and writes.
Availability / ReliabilityWeb and app tiers span two AZs with at least two instances each; ELB health checks make the ASGs replace failed instances automatically; Docker restart policies; DB host has EC2 auto-recovery, data on a separate EBS volume and daily S3 backups.Single DB instance in one AZ is the main single point of failure → 3-node replica set across AZs or DocumentDB (blocked on this account). Single NAT Gateway → one per AZ.
ElasticityTarget-tracking policies scale out and back in automatically: average CPU 50 % (both tiers) and 1,000 ALB requests per target (web tier).Scale-out takes ~2-3 min (boot + image pull); a pre-baked AMI or Fargate would react faster.
SecuritySection 5: SG chaining, private subnets, least-privilege IAM, Secrets Manager, encryption at rest, IMDSv2, no SSH, scanned immutable images, scoped CI credentials.HTTP only (no domain for an ACM certificate) → Route 53 + ACM + HTTPS listener and AWS WAF. App→DB traffic is VPC-internal but not TLS. CI uses an access key because OIDC is blocked.
Maintainability / DeployabilityAll infrastructure in Terraform; every push runs tests, an integration test, image build, rolling deploy and smoke test automatically; releases are SHA-tagged and roll back by redeploying an older commit; zero manual server access.Terraform is applied manually with local state → move state to S3 + DynamoDB locking and add a plan/apply stage to the pipeline.
Performance / LatencyNginx serves static assets with gzip and one-year immutable caching; load is spread by ALBs; all tiers are in one region and VPC; gp3 storage for the DB; MongoDB indexes on user+date and user+category.Add CloudFront in front of the web tier for global users and a cache (ElastiCache) for report aggregations.
Cost-EfficiencyFree-tier-eligible t3.micro/t3.small instances; ASGs idle at the minimum of 2; a self-managed DB instead of a ~$70/month managed cluster; one NAT Gateway; ECR lifecycle and 14-day log retention; whole stack destroyable with one command.See Section 8 for further measures.
PortabilityAll three tiers are standard Docker images (nginx-unprivileged, node, mongo:7) configured only through environment variables; the same images run locally with docker compose, on EC2 here, and could run unchanged on ECS, EKS, AKS or GKE; switching to Atlas or DocumentDB only changes MONGO_URI.Terraform code is AWS-specific and would need rewriting for another provider.

The deployment runs on AWS Free-plan credits ($100), so the evaluation period costs nothing out of pocket. Figures are on-demand estimates and should be confirmed with the AWS Pricing Calculator.

Cost optimization measures:

  • Replace the NAT Gateway with VPC endpoints (free S3 gateway endpoint plus ECR, SSM, Secrets Manager and CloudWatch Logs interface endpoints) or a NAT instance, removing most of the ~$43/month NAT charge.
  • Serve the React build from S3 + CloudFront (or use a single ALB with path routing), removing the two web instances, their public IPs and one ALB (~$50/month).
  • Schedule non-production environments: scale ASGs to zero and stop the DB host outside working hours, or terraform destroy when idle.
  • Graviton and commitments: t4g instances are ~20 % cheaper (multi-arch images), and Savings Plans cut steady-state compute by 30-40 %.

9. Conclusion

The Expense Tracker was successfully containerized and deployed on AWS as a secure three-tier architecture: a public web tier and a private application tier, each in its own Auto Scaling Group behind its own load balancer across two Availability Zones, and an isolated, authenticated, encrypted and backed-up database tier. Container images are stored in Amazon ECR, and a GitHub Actions pipeline tests, builds, pushes and performs zero-SSH rolling deployments on every change, verified by an automatic smoke test. Five cloud-native enhancements were implemented (S3 object storage, persistent EBS block storage, CloudWatch logging and monitoring, Terraform infrastructure as code and a cost estimate). The main remaining limitations — a single-instance database, HTTP-only access and key-based CI credentials — are consequences of the Free-plan account restrictions and are documented above with concrete improvements.
